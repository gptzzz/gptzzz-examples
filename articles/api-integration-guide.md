# 从一次请求开始：中文 API 中转接入与排错记录

> 本文基于 Semrush Content Toolkit AI 文章生成器的既有草稿 015，经 Codex 编辑、技术审校与项目适配。它不是未经修改的平台原稿，也不是服务实测报告；本文未使用真实密钥调用模型，不包含性能、价格或成功率结论。

接入 API 中转服务时，最有用的第一步往往是把问题缩小到一次请求：固定地址、密钥来源、模型 ID 和输入内容，再记录实际响应。业务代码、SDK、代理、重试和并发同时参与时，即使出现了错误，也很难判断是哪一层出了问题。

一份清楚的接入记录应回答三个问题：请求准备发到哪里，服务实际返回了什么，这些证据能支持什么结论。收到一段通顺的回答，只是其中一个观察结果。

## 先把地址、密钥和模型分开

本文以 [KaiGPT（gptzzz.ai）](https://gptzzz.ai/) 的公开接入说明为配置示例。它提供独立第三方 API 服务，不代表 OpenAI 或其他模型提供商。根据 2026 年 9 月 9 日读取的[接入文档](https://gptzzz.ai/docs/)，OpenAI 兼容聊天请求采用以下约定：

| 配置项 | 示例中的含义 |
|---|---|
| Base URL | `https://gptzzz.ai/v1` |
| 完整聊天地址 | `https://gptzzz.ai/v1/chat/completions` |
| 请求方法 | `POST` |
| 认证头 | `Authorization: Bearer <用户自己的专用 API Key>` |
| 内容类型 | `Content-Type: application/json` |
| 模型 ID | 从当前账户复制的精确标识；不设置猜测的默认型号 |

Base URL 和完整请求地址不能互换。客户端如果会自行追加 `/chat/completions`，配置应停在 `/v1`；否则可能拼出重复路径。不同协议还可能使用不同认证头和请求体，不能因为同属一个网关，就把 Claude Messages 与 OpenAI 兼容聊天的配置直接混用。

地址、密钥和模型 ID 应分别配置。将密钥放在本机环境变量或服务端密钥管理中，能减少代码里的硬编码，但环境变量本身不是加密保险箱：不要打印它，不要提交含真实值的 `.env`，也不要把它传到浏览器前端。

公开文档没有给出可确认的具体模型清单和价格。某个型号出现在教程中，不代表当前账户可以调用；示例里的模型占位符必须先替换为账户实际可用的 ID。

## 第一条请求只验证基础链路

先用短小、自己编写的文本，暂时不加入图片、文件、工具调用和长对话。请求体可以保持为下面的结构；其中模型字段仍然是占位符：

```json
{
  "model": "MODEL_ID_FROM_YOUR_ACCOUNT",
  "messages": [
    {"role": "user", "content": "请只回复：接入检查"}
  ],
  "stream": false
}
```

发起真实请求前，应先确认该账户的额度和计费规则。一次短请求也不等于免费请求，失败或取消后是否计费同样不能靠猜测。

curl 适合建立这份最小记录，因为请求方法、地址、请求头和正文可以直接检查。不过，curl 仍可能受本机配置文件、环境代理和命令参数影响。需要核对实际运行环境，不能把“使用 curl”当作已经排除了所有客户端变量。

配套的[首个请求说明](../docs/first-request.md)用于准备和运行请求。阅读命令时，先确认它会访问的主机和路径、是否跟随跳转、是否重试，以及输出会保存到哪里。不要把真实密钥贴进公开命令记录或 Issue。

## 保存一条足够排错的记录

“只保留一个请求”的目的是减少变量，不是要求删除线上系统的保护措施。应在独立测试脚本或测试环境中关闭额外重试、暂停并发，让一次执行与一次观察相对应。无法控制网关或上游是否重试时，应把这一点记为未知。

一条记录通常需要以下字段：

- 带时区的请求时间，优先使用 UTC。
- 客户端及版本、目标主机、请求路径和模型 ID。
- HTTP 状态码、内容类型、可用的请求 ID 和耗时。
- 是否收到完整 JSON、正文是否存在、结束原因是什么。
- 服务实际提供的用量字段，以及失败时可安全保留的错误类型。

不要默认保存完整提示词、响应正文、请求头或原始异常。错误消息也可能回显敏感内容。对外分享前，应重新检查记录，只保留复现所需的脱敏字段。响应头没有请求 ID 时写“未提供”；响应没有 `usage` 时写“用量未知”，不能记成零费用。

## 按失败发生的位置缩小范围

先区分连接问题、HTTP 拒绝和响应内容问题，再决定修改哪个变量。

| 现象 | 先检查什么 |
|---|---|
| 域名解析或连接失败 | 目标域名、本机网络、代理和连接超时 |
| TLS 证书错误 | 域名匹配、证书链、本机时间和代理证书；不要关闭证书校验来掩盖问题 |
| 400 / 422 | JSON 格式、必填字段、参数类型及组合 |
| 401 | 密钥是否属于当前服务、环境变量是否进入运行进程、Bearer 格式是否正确 |
| 403 | 模型权限、项目策略或入口访问限制；单靠状态码不能确定身份已经验证成功 |
| 404 | 是否重复或缺少 `/v1`、资源路径是否正确、模型 ID 是否存在或获授权 |
| 429 | 是速率限制，还是额度不足；额度不足时反复重试没有帮助 |
| 5xx / 超时 | 入口、网关或上游故障，保存已有证据后再判断是否适合有限重试 |
| 返回 HTML，JSON 解析失败 | HTTP 状态、内容类型及最终访问地址，排除登录页、拦截页或错误路由 |

这些是排查方向，不是对 gptzzz.ai 每种错误响应的实测断言。错误可能由网关生成，也可能来自上游；服务不一定始终返回相同的 `error.type`、`error.code` 或请求 ID。

重试前还要检查业务操作是否可以重复执行。超时只表示客户端没有按时收到结果，并不能证明服务端没有处理请求。对于可能产生额外费用或业务副作用的任务，不应立即整单重放。具体处理可继续看配套[排错说明](../docs/troubleshooting.md)。

## 把“接口返回”与“任务通过”分开

HTTP 2xx 和有效 JSON 说明请求取得了一个可解析的响应，仍需核对输出及结束原因。以普通文本聊天为例，可以检查 `choices` 是否存在、文本是否为空、`finish_reason` 是否符合任务预期。输出达到长度上限与正常结束应分别记录。

非流式请求成功，也不能证明流式输出、工具调用、结构化输出或 Responses API 已经兼容。每增加一种能力，都应准备独立样本，并定义结束和失败条件。流式连接在 HTTP 200 之后仍可能中断；收到第一个文本片段不等于完成。

请求指向 gptzzz.ai，能够说明客户端使用了该入口；响应中的模型名称或回答风格，不能独立证明实际上游型号。若需要核对路由，应结合平台能够提供的请求记录，并保留无法验证的边界。

## 让结论可以被下一次验证

保留固定的脱敏输入，记录配置和客户端版本。调整时一次只改一项，例如模型 ID、路径或某个请求参数，并保存前后差异。这样即使问题消失，也能知道变化来自哪里。

离线测试可以验证配置校验、URL 拼接、响应解析和错误处理；它无法证明某个账户有额度、某个模型在线，或真实调用速度达到某个水平。真实请求记录则应限定到实际使用的账户、模型、时间和样本，未经测量的项目直接写“未验证”。

一篇可信的接入文章不需要堆出大量成功截图。它需要让读者分清配置说明、测试方法和实际结果，并能沿着保留下来的记录继续排查。
